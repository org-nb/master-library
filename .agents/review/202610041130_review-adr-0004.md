# Design review: ADR-0004 (SvelteKit front-end and agentic workflows)

**Date:** 2026-10-04
**Scope:** `docs/adr/0004-design-sveltekit-frontend-for-catalog-and-agentic-workflows.md` (uncommitted draft), cross-checked against the committed ADR-0003 revision and the oxivault source tree.
**Verdict:** The direction is sound: a thin static SvelteKit app over the oxivault API, with server-side agent execution and API-enforced role boundaries, is the right shape. Do not accept as-is. There is one internal contradiction (superforms + adapter-static), one unspecified prerequisite that blocks the whole browser-facing design (cross-origin auth for a static SPA), and a scope question (LLM orchestration inside oxivault core) that should be settled before rollout planning.

**Resolution (2026-10-04):** all six required changes were applied in the ADR-0004 revision. The chosen architecture (SvelteKit SSR server, oxivault co-located in the same container, same-origin cookie sessions, agent orchestration in app server modules) resolves findings 1, 2, 3, 5 and 6 structurally; finding 4 is fixed by the ETag-threaded conditional-PUT patch contract. Minor findings 7-8 are incorporated (sanitized agent output, CSP, 100 KB JS budget, WCAG 2.2 AA); finding 9's design-doc drift remains tracked as housekeeping.

---

## Strengths

- Server-side LLM execution with no provider keys in the browser, and API-enforced authorization with UI role checks as convenience only: correct trust model, consistent with ADR-0003.
- SSE over WebSockets is the right call for one-way streaming; the typed message envelope (`token`, `tool_call`, `tool_result`, `evidence`, `final`, `error`) is a good contract sketch.
- Explicit confirm-before-apply for agent writes, diff previews, and audit logging are the right safety posture.
- Rollout ordering (reader surfaces, then librarian, then agent panels, read-only agent first) is sensible.
- Option analysis is honest about the trade-off (fewer ready-made components, more internal UI work).

## Findings

### 1. `sveltekit-superforms` contradicts `adapter-static` — major

Superforms is built around SvelteKit server form actions. With
`adapter-static` there is no server runtime: no actions, no server
`load`, no server-side validation hooks. Superforms in a static SPA
degenerates to a client-side form helper while its main value
(schema-driven server validation) lives where the schema belongs anyway:
the oxivault API. Recommendation: drop superforms from the ADR; use zod
for client-side pre-validation plus plain fetch with typed API errors.
If server form actions ever become wanted, that is an argument for a
non-static adapter, which is a different decision. Also verify
superforms' current maintenance status before taking any dependency on
it; the Svelte ecosystem's form-helper churn is exactly the "fast-moving
UI fashion" this ADR says it wants to avoid.

### 2. Cross-origin auth for a static SPA is unspecified — major, blocking

The ADR requires "role-aware auth endpoints and session/token contracts"
from oxivault but does not say how a browser-held front-end on a
different origin authenticates. The options have materially different
consequences:

- **HttpOnly cookies** require `SameSite=None; Secure` for
  cross-origin use, which reopens CSRF exposure on all mutating routes
  (needs CSRF tokens or an origin allowlist at the API).
- **Bearer tokens in JS** avoid CSRF but expose tokens to XSS and need a
  refresh strategy.

Pick one (recommendation: short-lived bearer tokens held in memory with
a refresh flow, given the API host already needs CORS allowlisting
per ADR-0003), and state it in the ADR. Also resolve the reader-role
ambiguity: ADR-0003 defines a read-only audience role, but it is unclear
whether browsing the published catalog requires authentication at all.
If readers are anonymous, the reader agent panel is an unauthenticated
LLM cost faucet and needs rate limiting or a lightweight identity gate;
the ADR is silent on LLM cost control generally.

### 3. SSE with authentication rules out native `EventSource` — correction

`EventSource` cannot set `Authorization` headers and only issues GETs.
With bearer-token auth (finding 2), agent streaming must use
`fetch()` with a `ReadableStream` reader parsing the `text/event-stream`
body. The ADR's transport choice is still right; the implementation note
belongs in the ADR so the front-end contract is buildable as specified.
Operationally: the API host's reverse proxy must disable response
buffering for the agent route, or streaming silently degrades to
chunk-at-a-time.

### 4. The agent patch/diff contract has no oxivault primitive — major

`propose_metadata_patch` and `apply_patch` imply structured patching of
note frontmatter. oxivault currently supports only whole-note
`PUT /notes/{path}` with `If-Match` optimistic concurrency. If the agent
composes a full-note update from a read it performed earlier, a
concurrent librarian edit is silently clobbered unless the agent's read
ETag is threaded through the apply step, which the ADR does not specify.
Recommendation: either add `PATCH /notes/{path}` (JSON Patch over
frontmatter) as an upstream oxivault extension in ADR-0003's list, or
state explicitly that apply = conditional PUT with the ETag captured at
propose time. Also specify the patch format (the ADR references JSON
Schema but never defines the diff schema) and that `stage_publish` and
`apply_patch` must call the exact ADR-0003 pointer-publish operation,
never a parallel write path.

### 5. LLM orchestration inside oxivault core is an unexamined scope decision — major

ADR-0004 assigns "LLM orchestration + tool calls" to oxivault API
endpoints, but ADR-0003's required-extensions list (auth, CORS,
presign, key builder, place registry, lineage validation, pointer
publish) contains nothing agent-related. Two consequences:

- oxivault is a general-purpose open-source project; baking
  Master Library agent endpoints into its core couples its roadmap to
  this application. If that is intended, ADR-0003's extension list
  should say so. If not, the orchestrator belongs in a separate thin
  service (or an oxivault plugin/route module) that calls the same
  authenticated API the front-end uses, which also keeps the
  "authoritative validation and mutations in oxivault API" claim
  literally true.
- Provider selection, prompt/context construction from the vault
  (SPARQL results, triples, note bodies), conversation persistence, and
  cost/rate limits are all unspecified. The ADR should at minimum scope
  these as a separate agent-backend design doc rather than leaving them
  implied.

### 6. `adapter-static` SEO/prerender trade-off is unacknowledged — minor, decide now

A static SPA means catalog pages are rendered client-side: no SSR, and
prerendering is only possible for content baked at build time, which a
live catalog is not. If public teaching pages should be crawlable and
shareable with previews, this choice needs revisiting (adapter-node, or
Cloudflare Pages Functions with the SvelteKit Cloudflare adapter).
If SEO is genuinely unimportant for this audience, state that
explicitly so the decision is defensible later. Related: with a static
SPA every page load is API traffic; note a read-caching strategy
(oxivault already returns ETags; the front-end should use conditional
requests or `svelte: prefetch`).

### 7. Agent-output sanitization and CSP are missing — minor

Agent `final`/`evidence` output and tool traces rendered in the UI are
model-generated and partially model-controlled content. The ADR's
accessibility section mentions confidence qualifiers but no XSS
posture: render agent output as sanitized Markdown (no raw HTML),
define a CSP for the app, and never turn evidence links into unfiltered
URLs. This belongs with the "Safety and audit" section.

### 8. Vague measurable targets — minor

- "Keep initial payload minimal" should be a number, for example
  "reader routes: < 100 KB gzipped initial JS", checked in CI.
- "WCAG-aware" should be a conformance target, for example WCAG 2.2 AA,
  verified with an automated axe pass in the Playwright setup this
  project already uses for web-app testing.

### 9. Cross-document drift — housekeeping

The committed ADR-0003 revision (pointer publication, tier model,
place registry, expanded `publication_state`) supersedes parts of the
session design doc `.agents/design/202610041026_oxivault-r2-catalog-design.md`,
whose frontmatter schema (`versions`/`master`/`published_key`) and
two-step publish flow predate it. ADR-0004 itself is consistent with
the committed ADR-0003 (tiers, place filters, publish states, ETag
concurrency). Reconcile the design doc or mark the relevant sections
superseded so the three documents do not describe three different
metadata models.

## Required changes before acceptance

1. Remove `sveltekit-superforms` (finding 1).
2. Specify the browser-auth model and reader-role policy (finding 2).
3. Note fetch-based streaming instead of `EventSource` (finding 3).
4. Define the patch contract and its oxivault primitive (finding 4).
5. Decide where LLM orchestration lives and update ADR-0003's extension
   list or scope a separate agent-backend design (finding 5).
6. Acknowledge the SEO trade-off or change the adapter decision
   (finding 6).

Findings 7 to 9 are recommended edits, not blockers.

## Open questions for the author

- Is the published catalog anonymous-read, or does every reader
  authenticate (affects finding 2 and LLM cost exposure)?
- Is oxivault intended to grow application-specific agent endpoints
  (finding 5), or should the agent backend be a separate component?
- Does the public catalog need search-engine indexing (finding 6)?
